# Background import scheduling

Every accepted source uses one sequential copy/hash lane and a bounded preparation pipeline. Original bytes are unchanged, SHA-256 is computed during copying, and completed writes are flushed before validation. Preparation uses two workers on machines with at least 8 GiB RAM and three available CPU threads, otherwise one. Each worker runs sharp outside Electron with concurrency limited to one and keeps its own ExifTool process warm.

The pipeline reserves each original's complete size before copying. At most four candidates and 512 MiB of originals may be in flight, including the current partial copy and duplicates waiting for another candidate. A supported original larger than the budget runs alone. RAW decoding retains its existing input and time limits. Decoder fallback has lower admission priority than normal preparation, occupies a preparation slot, and permits only one active import fallback.

Hashes are reserved while candidates prepare. A waiting duplicate becomes the owner if the first owner fails. Only successfully published content counts as an imported batch duplicate. Publication rechecks the catalog under the shared mutation mutex, then promotes the complete bundle and commits its database record. Rendering contracts are unchanged.

## Repeat device imports

Device reviews enable **Import only missing photos** by default. The review keeps every discovered candidate visible, marks recognized photos **Already in library**, and reports separate known and new-or-unchecked counts across loaded and unloaded records. Known photos use the managed thumbnail instead of reading the device for another thumbnail. Their checkboxes are disabled while the option is enabled; selected counts and accepted transfer totals exclude them. Disabling the option restores their stored choices and retains ordinary copy/hash duplicate behavior. Bulk selection acts on the currently eligible candidates. The choice survives review restarts, broader device searches and device changes within the dialog; file/folder imports retain their existing behavior.

Catalog version 14 retains version 13 source observations and adds main-only `camera_imports` bindings and `camera_samples` caches. A binding contains the format volume identity, volume-relative path, managed photo ID, exact size, modification time, available creation time, and `full` or `sample` proof. Successful validated imports and hash-confirmed duplicates establish full bindings only after publication to a live original. Failed or cancelled imports do not learn unpublished originals. Successful deletion removes both bindings and samples transactionally; pending removal prevents reuse and failed Trash preserves bindings.

**Fast camera checks** is the default for each new dialog. Matching persistent bindings plus live managed originals outside pending removal exclude unchanged candidates using metadata alone. Recognition survives reinsertion, different reader ports, mount-path changes and changed filesystem inode/device observations. Active mount validation still checks disconnection, replacement, nested mounts and containment. Linux discovery uses filesystem type, filesystem UUID, optional partition UUID and volume size. Windows uses the format serial from `Win32_Volume`, filesystem type, optional partition GUID and volume size; macOS uses `diskutil` filesystem type, volume UUID, optional partition UUID and volume size. Reader serials, device nodes and mount paths do not enter persistent identities. Missing, zero or visibly duplicate identities disable durable metadata trust and use bounded recognition per review.

exFAT's serial identifies a format operation, not guaranteed physical media. Cloned cards may share it, and same-size edits with preserved modification and creation times may go undetected in Fast mode. This is an accepted tradeoff for unchanged camera originals with photographs added or deleted. [Microsoft's exFAT specification](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification#3111-volumeserialnumber-field) describes the format-time volume serial. No marker files are written to a card.

An unbound Fast candidate searches an indexed case-normalized filename and exact-size pool of live managed originals, limited to eight distinct photo IDs. Larger pools use ordinary copy/hash duplicate checking without sampling. The versioned sample digest covers four 64 KiB windows at the beginning, one-third, two-thirds and end. Overlaps merge, and files up to 256 KiB are read completely. Each eligible bootstrap candidate reads at most 256 KiB from the card and 2 MiB from managed originals. Managed samples cache locally under their immutable content IDs. One unique match establishes sample proof; no match or multiple matches leaves the candidate eligible. A metadata mismatch against an existing binding always enters normal copy/hash processing and cannot be rescued by sampling. Subsequent reviews with a stable binding read zero recognized original bytes. Without a stable identity, each review samples again, using cached managed samples.

**Full verification** checks complete source contents before recognizing a prior binding or legacy source observation. Unbound candidates without a prior observation enter the normal full copy/hash duplicate path. Sample-linked bindings require complete hashing, and sample agreement never becomes SHA-256 proof. Switching to Full clears unverified exclusions immediately, acknowledges promptly, and starts cancellable background checking. Import stays disabled until checking finishes; Cancel and the policy selector remain usable. Separate cancellation and generation checks prevent superseded hashes from changing review counts or creating a task. A demonstrated content mismatch remains eligible even if the review returns to Fast.

The typed bridge adds `ImportVerificationMode = 'camera-fast' | 'full'`, the optional fourth `chooseDevice` argument, and `setImportVerificationMode(sessionId, mode)`. Review responses include the mode and checking state. Policy changes await queued selections and preserve candidate IDs, explicit choices, grid scroll anchors and focus. The choice survives device changes, broader searches and review restarts within a dialog. File/folder imports retain full copy/hash behavior.

Before acceptance, device validation is forced fresh, selected recognized sources receive metadata/containment checks, and live library membership is rechecked before targets freeze. Fast does not hash or sample recognized contents again. Full hashes every source being excluded a second time. Delayed validation and cancellation cannot publish a task afterward. A removed managed original becomes eligible again. Accepted transfer totals remain fixed and existing foreground scheduling, deletion suppression and original preservation are unchanged.

Discovery is shared and coalesced to one request per three seconds during review. Review boundaries, acceptance and copying/resumption force fresh checks. Candidate ID and filename/size lookups are indexed, counts update incrementally, and membership refreshes run on catalog changes or acceptance instead of rescanning the review on every notification.

## Foreground priority

The priority order is active preview/editing and visible analysis, then requested merges or confirmed deletion, then background import. Merge and deletion share FIFO admission. Native preview, metadata inspection, analysis, merge inspection, computation and publication acquire priority before entering their queues. Nested calls inherit their admitted owner, so inspection and publication cannot block their own task.

Foreground demand stops new preparation admission immediately. The current copy chunk finishes; the partial original and hash state remain live while copying waits. Resuming requires fresh authoritative source and device validation. Existing preparation normally drains before foreground admission. Long import RAW fallback can be cancelled and requeued from its staged original; worker exit precedes temporary asset cleanup. Existing publication sections and OS Trash calls finish before handoff. Merge publication retains its durable journal boundary.

A completed idle merge review releases scheduling priority while retaining independent source pins. Idle photographs and speculative cache housekeeping hold no foreground priority. Renderer notifications identify a photo or review, an activity ID, a monotonic sequence and an active flag. Gestures, frame transfer/presentation and visible analysis send 500 ms heartbeats. Main expires missing heartbeats after two seconds and coalesces idle release for 150 ms. Completion, cancellation, blur, suspension, errors, navigation and window destruction release activity. Adjustment inputs still share the existing persistence and photo-wide Undo/Redo implementation.

## Source and mutation safety

Source identity, size and timestamps are checked before and after copying, and again after a pause. Device checks use fresh volume identity and containment validation rather than cached discovery results. Confirmed disconnection or replacement stops new source work. Fully copied and validated staging may finish, and the task records one source error plus remaining unprocessed files. Reconnection requires a new explicit import.

Successful deletion suppresses that content hash for the currently accepted import. Suppression is checked after hashing and before publication, and appears as **Skipped after deletion**. Failed or unattempted targets stay eligible; another explicit import may reimport deleted content. Historical imported counts remain unchanged by later deletion. Trash restoration, source pins and recovery journals remain authoritative. An unresolved removal or merge publication journal prevents further mutations until recovery.

Accepted file and byte totals stay fixed. Overall progress counts resolved files, while copied bytes, copied/prepared counts, active copying throughput and waiting reasons appear separately. An active merge/deletion occupies the status bar while task details retain the waiting import. Disposing import review does not cancel an accepted task. Cancellation unblocks paused waits, awaits native workers, preserves committed photographs and removes only unpublished staging.

## Verification and measurements

Use the registered targets `work-scheduler`, `import-pipeline`, `import-foreground-ui` and `import-preparation-raw` for focused functional verification. Their gates cover overlap, reserved staging, priority, nested ownership, idle resumption, duplicate promotion, source replacement, paused-copy validation, fallback interruption, deletion suppression, unresolved journals, merge pins and cancellation cleanup. Existing import, device, deletion, merge, preview and workspace regressions remain registered separately.

Repeat-import targets are `camera-recognition` (Node), `camera-import` (service), and `camera-review-ui` (Electron). They cover persistent format identity, reader/remount reuse, changed metadata, bounded legacy bootstrap, sample ambiguity, Full hashing and cancellation, policy/selection queues, stale snapshots, acceptance guards, deletion, migration and the 1100 × 700 console layout. `import-source-records`, `import-missing` and `import-missing-ui` retain legacy observation and Full-mode regressions. Adapter fixtures exercise Linux, Windows and macOS extraction; physical readers and native platform discovery still require hardware evidence.

`npm run verify -- --target camera-import-performance` uses one worker to measure legacy bootstrap separately from a restarted repeat review with 1,000 known originals plus new files. It records byte counts, known-thumbnail/hash/copy counts, selected transfers and timings under the invocation's `artifacts/verification/` directory. Known originals must cause zero content reads, thumbnail reads, hashes or staging copies during repeat review and acceptance. The isolated local fixtures measure software behavior, not physical exFAT reader throughput. Any real-card measurements must use an isolated library/profile and read-only sources.

`npm run verify -- --target import-performance` records three isolated fixture runs with total time, copying time/throughput, preparation stages, first publication, main/native CPU and RSS, and staging peaks. Set `LUMA_IMPORT_BENCHMARK_SOURCES` to a JSON array of source paths and `LUMA_IMPORT_BENCHMARK_PHASE` to an artifact label for the same SD-card subset. Measurements and comparisons belong under `artifacts/verification/`. Source files are read only and libraries are temporary. Warm OS-cache throughput does not establish physical reader throughput; measure copying separately with source cache eviction when supported, without globally dropping caches or interrupting a user import.

On verified Linux hardware, `LUMA_IMPORT_BENCHMARK_COLD=1` uses Python's `POSIX_FADV_DONTNEED` for only the selected clean source files before each trial. Compare cold runs only with matching cache policy. Cached serial measurements remain a separate processing comparison.

Set `LUMA_BENCHMARK_IMPORT_ACTIVE=1` when selecting `hdr-interaction-benchmark` and `hdr-slider-benchmark` to retain their existing presentation and settling gates during an accepted background import. Physical input delivery and display scanout remain outside these measurements. Windows/macOS hardware support needs separate verification.

## Repeat-import acceptance

October 11, 2026, catalog version 14: **295 distinct cases passed** across four explicit invocations, with no latest failures or skips. The new feature has four Node, fourteen service, four Electron and one performance case. Static checks and affected device/progressive review, normal/background/foreground import, library, deletion, stack, history migration and typed bridge regressions passed. Runs took 42.98, 25.97, 68.83 and 33.21 seconds; the third retained the routine budget warning and all assertions. Evidence and earlier failures remain in `artifacts/verification/2026-10-11-camera-fast-acceptance/summary.md`.

The isolated one-worker measurement used 1,000 small synthetic originals plus two new files. Bootstrap took 884 ms and read 18,890 bytes each from card fixtures and managed originals; separate large-file cases exercise the maximum sample budgets. A restarted repeat review took 352 ms, with **zero content reads, source thumbnail requests, full hashes or staging copies for known originals** through Fast acceptance. Only the selected new file transferred. These warm local fixture measurements do not establish physical exFAT reader throughput. Physical readers, native Windows/macOS discovery, native pickers and real system Trash remain unverified. This is scoped feature verification, with no comprehensive checkpoint.
