# Experimental Sony RAW HDR preview

This milestone adds a separate HDR processing identity for verified Sony ZV-1 family compressed Bayer RAW modes. Linux is the verification platform. macOS and Windows remain unverified. Physical luminance is unmeasured: no meter is available, and relative brightness or reported headroom must not be presented as calibrated nits. The user visually confirmed the isolated Linux diagnostic’s HDR/SDR difference.

## Processing contract

Settings version 6 and catalog schema 9 distinguish `legacy-sdr-v1` from `hdr-v1`. Migration is transactional and marks existing photographs, including photographs without edit histories, as legacy. **Upgrade to HDR** preserves values in one undoable history entry. Display preferences never change processing identity or edits. The experimental new-import default is enabled through `HDR_IMPORT_DEFAULT`. Regression profiles explicitly select legacy imports; HDR profiles exercise the production default.

`hdr-source-v1` stores Float32, straight-alpha, scene-linear Rec.2020/D65. Black levels, black-subtracted nominal sensor maximum, camera white-balance gains, gain restoration, fixed source reference white, decoder/profile versions, orientation and available source saturation thresholds accompany every working asset. Only the registered Sony three-channel, square-pixel, approximately 3:2 `sony_arw2_load_raw()` mode is eligible. Other modes retain legacy processing.

LibRaw preparation uses linear 16-bit camera RGB, highlight mode 1 (unclipped), automatic brightness disabled, maximum adjustment disabled, and explicit camera gains. It normalizes gains by their maximum. Restoring `max(gains)/min(gains)` in Float32 before color conversion recovers the common legacy camera scale. GPU AHD uses the same nominal maximum, black subtraction and normalized gains. The 16-bit AHD stages therefore operate on normalized sensor values before gain restoration, rather than clipping an already amplified display image. Sensor saturation counts use reported `linear_max` thresholds; unknown thresholds are unavailable, never inferred from display white.

The fixed source white follows the existing neutral-source histogram policy before lens or user edits. It is recorded once in normalization and never derived from the display. The existing camera matrix, white-balance and lens providers are reused; this is not new camera characterization. Lens correction and orientation are applied once. Negative conversion results and values above white survive the working asset.

`hdr-adjustments-v1` retains exposure, contrast, highlights, shadows, whites, blacks and camera-aware white balance in the existing order and ranges, using Rec.2020 luminance coefficients. Alpha is separate. CPU fallback consumes the same HDR source, rather than a clipped SDR decoder fallback.

## Output and analysis

`hdr-output-v1` preserves luminance through 0.75 reference white. For luminance Y above that knee and target peak H, the shoulder is `0.75 + (H - 0.75) * (Y - 0.75) / (H + Y - 1.5)`. A radial chroma compression approaches the output gamut boundary smoothly beyond 90% of the available distance from the equal-luminance neutral. The output is encoded once with the extended sRGB transfer function into Display-P3 where available, otherwise sRGB. GPU computation retains Float32; the disposable presentation surface is `rgba16float`. SDR has peak 1; HDR uses the reported linear headroom. UI brightness stays SDR.

Auto, HDR and SDR are workspace preferences. HDR requests fall back with a reason if hardware WebGPU, extended canvas configuration or valid headroom is unavailable. Chromium’s logarithmic headroom is converted with `2 ** stops`. Monitor/headroom changes, focus, resize, resume and device loss trigger re-evaluation. Before and After use the same current target. The renderer remains sandboxed with context isolation; window-management permission is limited to the trusted top-level application window. No sandbox-disabling launch flag is added.

`hdr-analysis-v1` provides Working HDR and Output domains. Both use 256 log-luminance bins from −16 to +16 stops, with zero, negative, underflow and overflow counts outside the bins. Working analysis is independent of display state. Output analysis identifies source values exceeding headroom, gamut compression and actual output clipping separately; above-white values are not automatically clipped. RAW saturation remains a separate sensor-site report. These diagnostics and individual pixel inspection are available through MCP; the everyday workspace keeps minimal readouts. No absolute luminance is claimed.

The inspector shows one output RGB histogram (`rgb-histogram-v1`), separate from the unchanged log-luminance statistics. SDR has 256 encoded bins; HDR adds 256 logarithmic bins in an equal-width right half. Reference white belongs to SDR bin 255. HDR bins cover 0 through at least +4 stops, expanding to the ceiling of reported headroom; the axis never depends on photograph contents. The histogram follows Before or After (After in split), and CPU fallback uses its actual SDR target. The visible HDR toggle marks output clipping; detailed warning counts remain in MCP statistics. Bin navigation and numerical screen-reader descriptions remain available. The divider and stop markings follow [Adobe's HDR histogram reference](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/hdr-output.html).

Interactive histograms sample at most 65,536 pixels during the validated foreground load in a worker. Exact committed statistics stream the entire working asset through the processing worker. Overlay pyramids OR warning bits so isolated events survive reduction. Revision and display-generation conflicts reject stale exact requests. `luma_get_photo_statistics` without domain options preserves the original SDR response; explicit `working-hdr` or `output` requests use the HDR contract. Output requests select `sdr` or `current`; current requires the display generation returned by `luma_get_display_state`. `luma_set_preview_preference` and `luma_upgrade_photo_processing` share the UI’s application API and history.

`luma_get_photo_pixel` uses the same domains, output targets and conflict checks. Inputs also include integer `x` and `y` in the authoritative decoded/corrected image, plus `photoId` and `expectedRevision`. It samples committed light/white-balance edits from a leased working source, including durable merged masters, in the bundled processing worker. Only the requested 64-row strip is read and hash-validated; file size, descriptor layout, finite channels and alpha bounds are checked. The result includes photo/revision/rendering identity, dimensions, coordinates, domain/color space, linear `rgb`, `alpha`, `relativeLuminance`, `referenceWhite: 1` and `stopsAboveReferenceWhite` (`null` for nonpositive luminance). Output responses include the applied target. Foreground preparation, edit changes, deletion and shutdown cancel outstanding work and release leases. This operation changes no pixels, catalog schema or rendering version.

## Direct preparation and diagnostics

`requestHdrPreview` returns a typed source-only response with native dimensions and a validated Float32 descriptor. It never requires an RGBA8 proof or a subsequent editing-preview request. Cache v8 stores source-only entries separately from proof variants, within the same leased 2 GiB LRU. Source identity includes decoding, normalization and lens settings, while light edits and display targets reuse that entry and the active GPU texture. Default MCP statistics still generate an SDR proof on demand; explicit HDR statistics read the source directly. Catalog and settings versions are unchanged.

`luma_get_display_state` includes detected monitor, reported headroom, adapter, canvas support and permission information separately from the requested preference and actual presentation. The badge opens keyboard-accessible display details. Explicit HDR requests that display SDR include the fallback explanation. No-headroom reports remain authoritative. Monitor listeners are installed before GPU checks and remain active throughout asynchronous probes. All known displays are observed, and a lightweight one-second metadata comparison while visible catches missed compositor events without repeatedly probing the GPU. Monitor events, window moves, focus, resize, resume and device loss invalidate probes; stale asynchronous probes are discarded. Monitor scale comes from that display when available; no primary-display or brightest-display guess overrides reported headroom.

`luma_get_preview_diagnostics` and `getPreviewDiagnostics` expose active photo/revision, source identity, preparation backend, cache hit, loading stage and preparation/presentation timings. Renderer reports must match the active photo/revision and current target generation. Selection latency ends after two animation frames following the submitted full-resolution draw. Strip read/hash/validation timings are sums and may exceed the elapsed stream time because work overlaps. Cached records retain the original preparation timings alongside the current request duration. These describe software presentation, not measured luminance.

## Resource bounds

Working files have a whole-file SHA-256 and contiguous 64-row hashes. Size, dimensions, finite samples and alpha are checked before presentation. Uploads and CPU transforms stream strips. The foreground worker reads one leased streaming response, validates each 64-row strip hash, finite channels and alpha, then transfers at most three outstanding strips with credit-based backpressure. This removes per-strip protocol request overhead without weakening integrity checks. Truncation, excess bytes and unexpected transport chunks fail the load; cancellation closes the response. CPU overlay analysis retains bounded range requests; MCP pixel sampling reads one strip in the processing worker. GPU completion is awaited per group of three, plus the final preparation fence. After a successful load, one validation worker stays warm for at most 30 seconds without retaining source buffers; cancelled or failed loads terminate their worker. The sample is retained for the active source; the histogram does not download a second full copy. Overlay scans start after presentation and stop when superseded. The renderer accounts for Float32 source texture/mips, upload strips, viewport surfaces, analysis storage and two bounded 1 MiB transport chunks within its 512 MiB presentation limit. The peak is the larger of upload and presentation allocations: upload strips are released before the canvas and analysis become active. The canvas stays unconfigured during upload, and resizing back below the limit restores GPU presentation after a memory fallback; CPU preparation keeps the decoded float frame and scratch strip within 384 MiB. A replacement that cannot fit displays a neutral loader/error. The existing 2 GiB disk LRU, active leases, one foreground request, cancellation, deletion and shutdown coordination remain in place. Display targets are transient presentation variants, not source cache identities.

## Fixed verification gates

- CPU and actual WGSL adjustment/output math versus an independently written Float64 reference: absolute error ≤ `2e-6 + 2e-5 * abs(reference)`.
- Exposure +1/−1 EV: within two Float32 ULPs.
- Camera RGB GPU AHD versus unclipped LibRaw before restoration: mean ≤ 4/65535; fraction exceeding 64/65535 ≤ 0.001.
- Corrected CPU/GPU working data: mean absolute channel difference ≤ 0.002, accounting for preceding AHD differences and interpolation.
- Exact analytic histogram counts and retained isolated overlay impulses; sampled CDF error ≤ 0.01 against exact fixture scans.
- Existing SDR preview regression gates remain 15%; warmed HDR interaction p95 ≤ 33 ms with analysis enabled. Full-resolution selection-to-presented latency targets are cold median ≤ 3,000 ms and cached-revisit p95 ≤ 1,000 ms.

Synthetic cases include 0, 0.18, 1, 2, 4, 16, signed colors, neutral/color ramps and extreme combined adjustments. Migration rollback, missing histories, upgrade/Undo/Redo/restart, CPU fallback, both Sony import-preview routes, MCP compatibility, cache cancellation and deletion are covered by the affected verification scopes. Evidence belongs in unique ignored `artifacts/verification/` directories. Screenshots establish layout only, never HDR luminance.

## Multi-monitor refresh and allocation follow-up — September 25, 2026

The monitor investigation found a listener gap while the renderer awaited GPU capability checks. Display listeners now survive pending probes, observe every known display, and detect metadata changes even when the compositor omits events. Regression coverage switches from SDR to HDR during adapter initialization, moves back without an event, and verifies that a later genuine zero-headroom report still selects SDR.

Native Wayland tracing then reproduced a separate Electron 44.3.0 / Chromium 152 defect: the compositor mapped the window to the Microstep display, but Chromium retained the LG display's `ScreenInfos` from before mapping. `getScreenDetails()`, monitor moves, resize and mode changes kept returning LG. A renderer reload after mapping immediately reported Microstep with 4.560 stops of headroom. This is not a genuine zero-headroom report from the HDR display.

`src/main/wayland-display.ts` now refreshes native screen information once per second while the window is visible on Wayland. The workaround is confined to the pinned Electron 44.3.0 runtime. Its internal `WebContents.setEmbedder` call with the same contents retains the current owner and synchronously invokes native `WasHidden`/`WasShown`, which refreshes `ScreenInfos` without reloading the editor or unmapping its surface. It does not choose the brightest display, override reported headroom, change fractional scaling, or expose a debugger endpoint. Hidden/minimized/loading windows are skipped and the timer ends on close. The renderer's existing generation checks accept only current capability probes. Review and remove or revalidate this internal API workaround when upgrading Electron.

The source paths explaining the behavior are [Electron's SetEmbedder implementation](https://github.com/electron/electron/blob/v44.3.0/shell/browser/api/electron_api_web_contents.cc) and [Chromium's ShowWithVisibility / UpdateScreenInfo path](https://github.com/chromium/chromium/blob/152.0.7977.78/content/browser/renderer_host/render_widget_host_view_aura.cc). ## Wayland keyboard focus

On October 5, 2026, native tracing reproduced the display refresh clearing WebContents focus while its owner window remained active, preventing physical Delete and Tab input from reaching the editor. Each refresh now records whether both the window and its contents were focused. If both remain alive, the window remains focused, and the contents lost focus, it restores native view focus with [WebContents.focus()](https://www.electronjs.org/docs/latest/api/web-contents#contentsfocus). The focused DOM control is preserved. Initially unfocused views and background windows receive no focus restoration, including a window deactivated during refresh. The deletion shortcut, numeric inputs, console, confirmation and system Trash behavior retain their existing handlers.

`npm run verify -- --target wayland-display --target photo-actions --target hdr-editor-ui` covered **82 distinct tests**: 75 Node cases including 12 new focus cases, four photo-action cases, and three HDR editor cases. The selection recorded **81 passes and one incorrect dialog-title assertion in 91.4 s**; after correcting the assertion to the existing single-photo title, the affected Wayland case passed in a **20.8 s focused rerun**. Type checking, lint, formatting and the build passed. The regression checks native WebContents and DOM focus, native Delete and Tab after multiple refreshes, numeric-field and console behavior, background-window focus, GPU presentation, screen metadata and pointer capture. Original evidence is retained in `artifacts/verification/2026-10-05T15-29-34.882Z-check-NVlR1I/`; the focused rerun is `artifacts/verification/playwright-1791214312474-cb7d8a2c-7225-492e-b8c1-f60533d984e0/`.

The user confirmed physical Delete after a five-second wait, Tab navigation, focus remaining with another application, and monitor/headroom updates in a verified temporary `dev:mcp` profile. Only the licensed Sony fixture was imported, and Trash was isolated inside that profile. Native focus and renderer observations are retained in `artifacts/verification/2026-10-05T15-50-26.519Z-wayland-focus-acceptance-eXzXzo/`; the development processes were stopped and the profile removed. This acceptance covers the local Linux/Wayland setup. Windows/macOS and physical HDR luminance remain unverified.

On October 6, 2026, held preview drags reproduced another consequence of `WasHidden`: each timer tick released pointer lock even when native focus was restored. The refresh now observes mouse-button presses in the main process through [before-mouse-event](https://www.electronjs.org/docs/latest/api/web-contents#event-before-mouse-event) and defers screen-information refresh until release. A view-only blur preserves the held-button guard while the owner window remains active. Window deactivation, hiding, minimization, a new main-frame navigation, or renderer loss clears unfinished presses. The timer and its observers are removed on close or refresh failure. Monitor updates resume on the next idle tick; the pinned runtime gate and focus-restoration rules remain in place.

The shared main/merge preview regression holds a locked drag over two timer ticks, starts another near the next tick, verifies continued relative motion and normal release/Escape/blur cleanup, and checks that refreshes resume. The HDR editor case also checks deferred refresh during a drag and subsequent native monitor, focus and GPU presentation behavior. These checks use isolated profiles and do not certify other platforms or physical HDR luminance.
