# Sony RAW HDR/SDR preview

The ordinary Linux editor's [preview scheduling policy](editor-responsiveness.md#ordinary-editor-preview-policy) now comes from main's confirmed app platform, with Float32 eligible gesture feedback, exact completed-frame reuse, 512-tile chunks and a final presentation fence. Other and unconfirmed platforms retain their previous reference/32/separate/cache-disabled policy until separately verified. This changes no working-source version, normalization, canonical refinement, RAW/merge preparation, export math or recovery ownership. Older build-flag commands below remain historical evidence, not current configuration.

This milestone adds a separate HDR processing identity for verified Sony ZV-1 family compressed Bayer RAW modes. Local Linux and built-in Mac Retina display evidence is recorded below. Windows and broader platform certification remain unverified. Physical luminance is unmeasured: no meter is available, and relative brightness or reported headroom must not be presented as calibrated nits. The user visually confirmed the isolated Linux diagnostic’s HDR/SDR difference.

## Processing contract

Settings v7 and catalog schema 17 select the pipeline automatically: supported RAWs and merge masters use linear `hdr-v1` working assets, while raster photos use color-managed `display-referred-v1` output. Fresh and current libraries are supported; older catalogs and older or unknown edit formats are rejected without rewriting their histories or deleting originals. Current numeric edits, revisions and redo branches remain intact across reopening. Unsupported RAW modes show an explicit unavailable state. There is no per-photo upgrade or legacy rendering branch.

`hdr-source-v2-capture-scale-1` stores Float32, straight-alpha, linear Rec.2020/D65. Preparation subtracts reported black levels, uses nominal sensor saturation, applies As Shot gains once, and retains signed channels and highlights. LibRaw automatic brightness and observed-maximum adjustment are disabled. `referenceWhite` and input exposure scale stay fixed at 1: photograph contents cannot normalize exposure. The LibRaw camera matrix and gain-restoration scale are approximations, without measured Sony color or exposure calibration. Only registered Sony three-channel, square-pixel, approximately 3:2 `sony_arw2_load_raw()` modes are eligible.

RAW preparation retains the existing `sensor-blend-v1` adaptation of LibRaw highlight blending when reported saturation thresholds are usable. It preserves mean camera intensity and leaves values below saturation unchanged. CPU and WGSL agree; missing thresholds disable the blend. Lens correction and orientation apply once. Merge preparation and Working statistics remain linear. Capture masters require the current `hdr-source-v2-capture-scale-1` descriptor. Retired `hdr-source-v1` masters are unsupported; opening a preview or export rejects them without rewriting or deleting their bundle bytes. Merged masters also require the current `sony-merge-v4` recipe. A pending publication with a valid unsupported source or recipe version is retained after common geometry/provenance checks, full master/strip and motion-mask verification, and gallery-preview presence checks; it is reported as a failed merge task while current photos remain usable. Historical manifests have no independent gallery JPEG hashes. Unsupported published or cached recipes reject before preview copies or export processing; their original bundle bytes remain untouched. Corrupt or inconsistent journals still block recovery.

## Output and analysis

The default is **linear preparation → white balance and Light edits → fixed Rec.2020/D65 ACES 2 HDR content → reference-proof presentation → canvas encoding**. See [the rendering contract, pinned reference, units and limitations](display-rendering.md). `hdr-content-v1-aces2-rec2020-1000-d65` records nominal 1000-nit peak, 100-nit reference and relative peak 10. `hdr-output-v6-content-proof-aces2-069b0bc3-v2` and `hdr-analysis-v4-content-aces2-069b0bc3-v2` identify output and analysis. These are software units, without measured panel brightness. Before uses neutral Light edits and As Shot white balance. Raster inputs preserve their authored appearance.

Interactive presentation caches canonical HDR content independently of headroom and gamut. Supported P3/sRGB conversion, channel limits and single extended-sRGB encoding account for the active display. SDR preview, CPU fallback and proofs render the existing SDR ACES rendition directly from working pixels. Same-photo edits and display changes retain the latest completed photograph and validated source upload. Interactive edits and cold navigation preserve normal detail, coalescing intermediate requests when rendering falls behind. Bounded 32-tile chunks retain the measured Mac batching gain; the internal eight-tile comparison remains available. Current latency and sustained-progress misses remain explicit. CPU fallback retains its bounded draft followed by full-resolution refinement. See [queue, cache bounds, sampling and memory policy](display-rendering.md#interactive-presentation).

Auto, HDR and SDR remain workspace preferences. Chromium's logarithmic headroom converts with `2 ** stops`; monitor changes, focus, resize, resume and device loss trigger re-evaluation. Headroom and gamut remain separate capabilities, and unavailable headroom stays explicit. The renderer and save listener remain mounted during fallback.

Three statistics domains have distinct meanings: `working-hdr` is adjusted scene-linear Rec.2020; `content-hdr` is the fixed HDR rendition; `output` is the presented HDR proof or direct SDR rendition. Pixel inspection follows the same mapping. The default UI histogram and HDR ranges describe content, including when SDR is displayed. Its RGB axis is fixed through +4 stops; only the capability marker and warnings follow the monitor. Content luminance exceeding reported headroom, channel clipping, gamut limitation and sensor saturation are separate indicators. Overlays do not feed measurements. Detailed numerical diagnostics and individual pixel inspection remain available through MCP; the everyday workspace keeps minimal readouts and accessible bin descriptions.

Photo-wide GPU analysis uses 8192 stable samples during gestures and 65536 after release, without a debounce. Its independent coordinator bounds readback to one active request and one latest pending snapshot; image presentation has its own GPU completion fence. Pending bins retain their own edit revision and visible status until the histogram converges to the displayed edit. Histogram controls and readouts remain mounted and curves retarget a short animation with reduced-motion support. Masks run separately. Exact committed requests stream all validated pixels and preserve revision checks. `irodori_get_photo_statistics` without a domain retains compatible SDR analysis; explicit `working-hdr`, `content-hdr` and `output` requests use relative units. Current presentation/diagnostic requests require `targetGeneration` from display state. Processing upgrades remain absent from UI, bridge and MCP.

`irodori_get_photo_pixel` uses the same domains, output targets and conflict checks. Inputs also include integer `x` and `y` in the authoritative decoded/corrected image, plus `photoId` and `expectedRevision`. It samples committed light/white-balance edits from a leased working source, including durable merged masters, in the bundled processing worker. Only the requested 64-row strip is read and hash-validated; file size, descriptor layout, finite channels and alpha bounds are checked. The result includes photo/revision/rendering identity, dimensions, coordinates, domain/color space, linear `rgb`, `alpha`, `relativeLuminance`, `referenceWhite: 1` and `stopsAboveReferenceWhite` (`null` for nonpositive luminance). Output responses include the applied target. Foreground preparation, edit changes, deletion and shutdown cancel outstanding work and release leases. This operation changes no pixels, catalog schema or rendering version.

## Direct preparation and diagnostics

`requestHdrPreview` returns a typed source-only response with native dimensions and a validated Float32 descriptor. It never requires an RGBA8 proof or a subsequent editing-preview request. Cache v9 stores source-only entries separately from proof variants, within the same leased 2 GiB LRU. Source identity includes decoding, normalization and lens settings, while light edits and display targets reuse that entry and the active GPU texture. Default MCP statistics still generate an SDR proof on demand; explicit HDR statistics read the source directly. This content/presentation change preserves source identities and prepared working assets; only derived output and analysis identities change. Originals, master bytes and edit history stay intact.

`irodori_get_display_state` includes detected monitor, reported headroom, adapter, canvas support and permission information separately from the requested preference and actual presentation. The badge opens keyboard-accessible display details. Explicit HDR requests that display SDR include the fallback explanation. No-headroom reports remain authoritative. Monitor listeners are installed before GPU checks and remain active throughout asynchronous probes. All known displays are observed, and a lightweight one-second metadata comparison while visible catches missed compositor events without repeatedly probing the GPU. Monitor events, window moves, focus, resize, resume and device loss invalidate probes; stale asynchronous probes are discarded. Monitor scale comes from that display when available; no primary-display or brightest-display guess overrides reported headroom.

`irodori_get_preview_diagnostics` and `getPreviewDiagnostics` expose active photo/revision, source identity, preparation backend, cache hit, loading stage and preparation/presentation timings. Renderer reports must match the active photo/revision and current target generation. Selection latency ends after two animation frames following the submitted full-resolution draw. Strip read/hash/validation timings are sums and may exceed the elapsed stream time because work overlaps. Cached records retain the original preparation timings alongside the current request duration. These describe software presentation, not measured luminance.

## Resource bounds

Working files have a whole-file SHA-256 and contiguous 64-row hashes. Size, dimensions, finite samples and alpha are checked before presentation. Uploads and CPU transforms stream strips. The foreground worker reads one leased streaming response, validates each 64-row strip hash, finite channels and alpha, then transfers at most three outstanding strips with credit-based backpressure. This removes per-strip protocol request overhead without weakening integrity checks. Truncation, excess bytes and unexpected transport chunks fail the load; cancellation closes the response. CPU overlay analysis retains bounded range requests; MCP pixel sampling reads one strip in the processing worker. GPU completion is awaited per group of three, plus the final preparation fence. After a successful load, one validation worker stays warm for at most 30 seconds without retaining source buffers; cancelled or failed loads terminate their worker. The sample is retained for the active source; the histogram does not download a second full copy. Overlay scans start after presentation and stop when superseded. The renderer accounts for Float32 source texture/mips, upload strips, viewport surfaces, analysis storage and two bounded 1 MiB transport chunks against independent RAM and GPU budgets captured once per presenter from Automatic or custom Preview memory settings. These budgets cover RAW/HDR GPU preview resources, not CPU fallback, other workers, process memory or physical driver residency. The peak is the larger of upload and presentation allocations: upload strips are released before the canvas and analysis become active. The canvas stays unconfigured during upload, and resizing back below the limit restores GPU presentation after a memory fallback; CPU preparation keeps the decoded float frame and scratch strip within 384 MiB. A replacement that cannot fit displays a neutral loader/error. The existing 2 GiB disk LRU, active leases, one foreground request, cancellation, deletion and shutdown coordination remain in place. Display targets are transient presentation variants, not source cache identities.

## Fixed verification gates

- CPU and actual WGSL adjustment/output math versus an independently written Float64 reference: absolute error ≤ `2e-6 + 2e-5 * abs(reference)`.
- Exposure +1/−1 EV: within two Float32 ULPs.
- Camera RGB GPU AHD versus unclipped LibRaw before restoration: mean ≤ 4/65535; fraction exceeding 64/65535 ≤ 0.001.
- Corrected CPU/GPU working data: mean absolute channel difference ≤ 0.002, accounting for preceding AHD differences and interpolation.
- Exact analytic histogram counts and retained isolated overlay impulses; sampled CDF error ≤ 0.01 against exact fixture scans.
- Existing SDR preview regression gates remain 15%; warmed HDR interaction p95 ≤ 33 ms with analysis enabled. Full-resolution selection-to-presented latency targets are cold median ≤ 3,000 ms and cached-revisit p95 ≤ 1,000 ms.

Synthetic cases include 0, 0.18, 1, 2, 4, 16, signed colors, neutral/color ramps and extreme combined adjustments. Migration rollback, missing histories, upgrade/Undo/Redo/restart, CPU fallback, both Sony import-preview routes, MCP compatibility, cache cancellation and deletion are covered by the affected verification scopes. Evidence belongs in unique ignored `artifacts/verification/` directories. Screenshots establish layout only, never HDR luminance.
