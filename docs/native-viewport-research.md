# Standalone native viewport research — retired candidate

The standalone Rust/winit host was an isolated maximized-window diagnostic. Its
retained native summaries explicitly report `acceptancePassed: false`. GPU queue
completion and synthetic replay are not actual in-app compositor presentation.
Production keeps the existing React/browser WebGPU presenter. The exact source,
Cargo lockfile, fixture schema, old commands and all failed/incomplete evidence remain
in the ignored [exact source archive](../artifacts/bazzite-native-20261019/archived-winit-viewport/manifest.json); active CPU/mask working-source
fixture consumers remain independent and supported.

The following bounded assessment is preserved from the October 19 source README. Its
pinned Electron/wgpu/winit API observations are historical, not a claim about future
versions or a completed Linux transport. Any eventual experiment must revalidate those
capabilities and all app color/identity/recovery/resource/cancellation gates before
selection. No permanent alternate presenter, feature flag or second queue is selected
by retaining this note.

## Bounded production-integration assessment

The standalone winit window is a diagnostic host, not the production viewport. The existing application already evaluates its viewport shaders on browser WebGPU; moving that work to Rust does not establish a GPU acceleration gain. Its current source transport is a main-owned, pinned working-asset lease, streamed through `irodori-photo` with strip validation into the browser GPU. React controls, revision/history ownership, native-target confirmation and recovery remain application contracts.

| Integration option                                      | Assessment on the pinned stack                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Embed the winit window inside Electron                  | Not a supported Wayland seam: [winit 0.30.13 parent windows explicitly exclude Wayland](https://github.com/rust-windowing/winit/blob/v0.30.13/src/window.rs#L456-L473). Electron `View`/`WebContentsView` does not expose a public arbitrary Wayland child-surface host. A parent/transient window is not an image view inside the React layout.                                                                                                                                                                                                                                                           |
| Native offscreen texture into the existing React canvas | A bounded integration candidate. Local Electron 44.3.0 types and [its pinned shared-texture API](https://github.com/electron/electron/blob/v44.3.0/docs/api/shared-texture.md) support imported Linux native-pixmap handles, renderer transfer and reference-release callbacks. Retain the existing app window and input model; remove the winit surface from this backend.                                                                                                                                                                                                                                |
| Assume zero-copy WebGPU import is solved                | Unsupported by the current evidence. [Electron 44.3.0's Linux import code](https://github.com/electron/electron/blob/v44.3.0/shell/common/api/electron_api_shared_texture.cc#L683-L734) duplicates plane FDs and enables GLES2/raster/display shared-image usages, while its Windows/macOS branch additionally enables WebGPU usages. A `supportsZeroCopyWebGpuImport` flag does not prove a working path. Its [pinned shared-texture tests run only on macOS arm64](https://github.com/electron/electron/blob/v44.3.0/spec/api-shared-texture-spec.ts#L10-L13). Linux behavior needs direct verification. |

The smallest useful application experiment is one opt-in, windowless native viewport backend for the actual managed Sony asset, Exposure and Fit/100%, with React and the default browser presenter retained. Main resolves a photo ID into the existing validated working-asset lease and supplies the worker's internal source handle and frozen shader/table identities. A narrow bridge uses session/request IDs, source identity, edit revision or explicit transient gesture state, epoch, input serial, viewport/view, target generation and rendering policy. It exposes no filesystem paths, native handles, arbitrary shaders or command runner. Persisted edits continue through the shared application API.

For Linux GPU transport, an output DMA-BUF must have a mutually supported format, modifier, stride and plane layout. Process-local FD numbers cannot be copied as JSON: a native FD transport such as Unix-domain `SCM_RIGHTS` must place them in the importing process. Wgpu 30's [single-plane DMA-BUF import helper](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/vulkan/device.rs#L470-L487) is an unsafe backend seam, not automatic export of this prototype's ordinary texture. GBM/Vulkan allocation, external ownership transitions and synchronization would require additional bounded implementation and measurement; they are not implemented here.

Use a two- or three-slot output lease pool and a latest-state request queue. Producer GPU writes must finish before publication unless a verified external-fence protocol replaces that wait; Electron's public import descriptor has no producer acquire-fence field. Main imports and transfers a frame to the existing main renderer. A sandboxed preload can own the receiver and a narrowly identified DOM canvas, draw the `VideoFrame` through a measured Canvas2D/WebGL path, then close/release it without exposing raw texture APIs. This is a feasibility proposal, not proof that those paths avoid internal copies or preserve HDR/P3. Reuse a slot only after `allReferencesReleased`, not an IPC/draw acknowledgement. Reject stale source/epoch/revision/target frames, and drain outstanding leases on navigation, deletion, shutdown and device loss. Preserve the completed-pixel recovery contract.

At an illustrative 2914 × 1258 viewport, three RGBA16Float output slots alone require about 84 MiB, before driver/Chromium ownership. A CPU RGBA8 readback/reupload would move about 14.7 MB per frame in each direction, approximately 0.88 GB/s per direction at 60 frames/s; it would retain the copy cost this experiment is intended to investigate. DMA-BUF can avoid that CPU transport but still incurs synchronization, import, color conversion and compositor work. Measure those costs and in-app visible cadence separately from native compute. First prove matched SDR-sRGB output, lifetime/cancellation, bounded memory and real React-window presentation; P3/HDR, recovery and background-load gates remain separate. Do not adopt the native viewport or start a speculative transport rewrite from the standalone-window timing alone. The [phase ledger](bazzite-native-engine.md) records the selected browser-presenter retention and retirement of this standalone candidate. This historical assessment does not leave a transport experiment required by the current goal.
