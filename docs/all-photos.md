# Library browsing

Library is a session-local browsing workspace beside Editor. Its Images navigation icon identifies the full photo catalog; Editor uses the sliders icon and contains a compact Photos panel. Library presents every managed photo independently of stack expansion, using the same selection, actions, background task registry and deletion confirmation as Editor. Selecting in the browser changes selection and browser focus; opening a photo explicitly changes the editor's active photo. Browser ranges retain the accepted query and execute in arrival order with other selection gestures. Deletion awaits this queue before freezing its confirmation targets.

Date, Month and Year headings can fold their thumbnail rows. Click a heading or focus its button and press Enter or Space. **Collapse all groups** reduces the current results to headings; **Expand all groups** reveals them again. Each grouping remembers its folds for the current session, including across searches and visits to Editor. Group counts and selection checkboxes remain available when folded, and selecting a folded group still includes every matching photo. Folding never changes selection or range membership. Photo keyboard navigation skips folded groups, and folding the focused photo's group clears browser focus without changing the editor's active photo.

The version-15 catalog migration creates `photo_browse` and `browse_state` in the existing migration transaction. The index stores validated camera calendar date/time, searchable metadata, import timestamp, photo ID and date origin. Search splits whitespace into case-insensitive literal terms; every term must appear in one of the indexed fields. It has no query language. Ordering is camera calendar date/time descending, import timestamp descending, then photo ID descending. Dates are validated without converting timezone offsets into the computer's timezone. Missing or invalid dates are last.

Import and merge publication update the index in their catalog transactions. Metadata refresh updates stored processing metadata and the index together. Photo removal deletes its index entry through a catalog trigger; successful mutations increment the browse revision. Original and edit-history records retain their existing contracts.

New merge manifests freeze the configured reference's date in the result photo and processing metadata, with a `merge-reference` origin naming that source. Legacy manifests remain immutable. Their index dates recover from surviving reference records during migration and remain in the result's independent index row after source deletion. A legacy result whose reference date cannot be recovered remains unknown.

The typed preload bridge exposes summaries, 60-photo chunks, photo locations, inclusive individual range references and complete section references. Summaries include matching and selected counts plus selections outside the query. Editing MCP exposes equivalent read operations without altering the existing flat-photo or stack-aware gallery APIs. Presentation reads can require a catalog revision; gesture reference reads retain their query and resolve against live managed records.

The app-owned row virtualizer computes responsive columns, section headers and fixed-height thumbnail rows. It renders the viewport plus two rows of overscan, requests only chunks containing nearby expanded photo rows, and caches at most 300 individual records (five 60-photo chunks of capacity). Folded groups keep their headers without photo rows or dedicated thumbnail requests. The record cache supports discontiguous expanded sections without leaving visible photos unloaded. Query and catalog generations reject stale chunks. Scroll restoration locates the first visible photo or folded heading after grouping or catalog changes. The hidden editor ignores zero-size and suspended preview measurements.

Verification targets are `all-photos-model` (Node), `all-photos` and `catalog-migration` (service), and `all-photos-ui` (Electron). Automated imports and deletion use isolated managed libraries and Trash adapters. Visual acceptance uses an isolated `dev:mcp` profile at 1100 × 700 with Console open; no performance benchmark or full checkpoint is implied by this feature.
